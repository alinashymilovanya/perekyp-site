# iPhone Monitor

Бот следит за объявлениями iPhone на Авито, считает потенциальную маржу и
присылает карточку сделки в Telegram.

## Как это работает

1. `src/iphone_monitor/avito_api_source.py` дёргает внутренний JSON-фид Авито
   (`https://www.avito.ru/web/1/main/items?locationId=...&categoryId=84`) с
   User-Agent мобильного приложения. HTML-страницы Авито с домашних IP закрыты
   капчей, а этот фид отвечает.
2. Цены всех увиденных объявлений складываются в SQLite
   (`listing_prices`), поэтому «рыночная цена» — медиана цен на такие же
   модель/память/состояние за последние 30 дней, а не по одной странице выдачи.
3. Маржа = рынок − цена − доставка − комиссия − резерв ремонта. Если маржа
   больше `NOTIFY_MIN_MARGIN_RUB`, карточка уходит подписчикам.
4. В ленте нет ни состояния, ни аккумулятора, ни описания — только название и
   цена. Страницы объявлений Авито отдаёт лишь жилым IP: из облака и с любого
   датацентра приходит HTTP 439 «Доступ ограничен». Поэтому чтение карточек
   вынесено на домашний компьютер:
   - бот, отправив уведомление, кладёт id в таблицу `detail_requests` и
     публикует `site/detail-requests.json` в репозиторий;
   - на ПК работает `tasks/detail_agent.py`: он берёт заявки и открывает
     карточку в настоящем Chrome пользователя через `browser-act` (профиль из
     `AVITO_BROWSER_ID`, сессия `AVITO_SESSION_NAME`) — сырой HTTP с того же
     адреса Авито режет ответом 439, а браузер с куками открывает страницу.
     Из DOM берутся состояние, ёмкость аккумулятора, цвет, SIM, продавец, время
     публикации и полный текст описания; ответ публикуется в
     `site/detail-results.json`. Если браузера нет, агент откатывается на
     обычный HTTP-разбор `window.__initialData__`;
   - бот забирает ответы, кэширует их в таблице `item_details` и присылает
     вторым сообщением «Подробности объявления». Если агент на связи, бот ждёт
     ответ до `DETAIL_WAIT_SECONDS` и сразу добавляет данные в первое сообщение.
   Резерв на ремонт считается по настоящему состоянию: «Новый» — 0 ₽, «Битый» —
   `REPAIR_RESERVE_BROKEN_RUB`, остальное — `REPAIR_RESERVE_USED_RUB`.
5. Если Telegram недоступен, уведомление не теряется: оно попадает в очередь
   `pending_notifications` и досылается, когда связь вернётся.

## Переменные окружения (файл `.env`)

Обязательные:

```env
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
LISTINGS_SOURCE=avito_api
```

Полезные:

| Переменная | Смысл |
| --- | --- |
| `AVITO_API_LOCATION_ID` | 107620 — вся Россия, 637640 — Москва и т.д. |
| `AVITO_API_QUERY` | Слово для поиска, по умолчанию пусто. Авито в этом канале игнорирует формулировку запроса и отдаёт всю категорию телефонов, поэтому реальная фильтрация идёт по названию объявления на стороне бота |
| `POLL_INTERVAL_SECONDS` | Пауза между опросами Авито, не меньше 180–600 (иначе 429). На практике безопасно 900 |
| `MAX_LISTINGS_PER_POLL` | Сколько объявлений просить за один запрос; 100 проверено, больше Авито не отдаёт |
| `NOTIFY_MIN_MARGIN_RUB` | Порог маржи для уведомления, сейчас 500 ₽ |
| `DELIVERY_RUB`, `COMMISSION_RUB` | Расходы на доставку и комиссию |
| `REPAIR_RESERVE_USED_RUB`, `REPAIR_RESERVE_BROKEN_RUB` | Резерв на ремонт б/у и битых |
| `TELEGRAM_TRANSPORT` | `mtproto` или `botapi` |
| `TELEGRAM_PROXY` | `host:port:secret` MTProto-прокси (для mtproto) |
| `DAILY_SUMMARY_TIME`, `SUMMARY_TIMEZONE` | Время ежедневной сводки |
| `DETAIL_ENABLED` | Дочитывать карточку объявления (1/0) |
| `DETAIL_RELAY_ENABLED` | Читать карточки через домашний агент (1/0) |
| `DETAIL_WAIT_SECONDS` | Сколько ждать ответ агента в цикле, по умолчанию 40 |
| `DETAIL_RELAY_POLL_SECONDS` | Как часто проверять ответ агента, по умолчанию 5 |
| `DETAIL_MAX_PER_CYCLE` | Прямой режим: сколько карточек открывать за цикл |
| `DETAIL_PAUSE_SECONDS` | Прямой режим: пауза между карточками |
| `DETAIL_COOLDOWN_MINUTES` | Прямой режим: отдых после ответа 429/403 |

## Домашний агент

Агент — обычный Python-скрипт, работает рядом с ботом на ПК пользователя:

```powershell
D:\tg\tasks\run-detail-agent.ps1
```

Он читает `site/detail-requests.json` из `GITHUB_REPO`, открывает нужные
карточки в Chrome через `browser-act` (пауза 12 секунд между страницами),
пишет `site/detail-results.json` и держит отметку `generated_at` свежей (раз в
5 минут), чтобы бот знал: агент на связи. Если Авито показывает страницу
проверки IP («Страница не загрузилась из-за проблем с IP», «Доступ ограничен»),
агент не долбит сайт: пауза от 10 минут с удвоением до 3 часов. Лог —
`data/detail-agent.log`.

## Ограничения ленты Авито

Проверено на живом фиде:

- Фраза поиска (`query`) и номер страницы (`page`) игнорируются: любой запрос
  отдаёт самые новые телефоны России. Поэтому страницы не листаются, а фильтр
  по iPhone идёт по названию объявления на стороне бота
  (`is_iphone_phone`), аксессуары, чехлы, часы и наушники отбрасываются.
- `limit=100` работает (~90 объявлений в ответе), из них реальных iPhone
  обычно 15–20.
- Rate limit жёсткий: серия из нескольких запросов подряд даёт HTTP 429 и
  блокировку IP на несколько минут. Поэтому интервал 900 секунд, а на 429 бот
  отступает минимум на 5 минут и не падает.

Следствие: примерно раз в 15 минут в историю попадает ~18 живых iPhone.
За сутки это ~1500 цен. Рыночная цена считается по медиане цен на ту же модель,
память и состояние за 30 дней. Двух цен достаточно, только если они расходятся
не больше чем на 15%; одна цена рынком не считается, и тогда уведомления по
этой модели нет — так отсекаются случайные «медианы из одной цены».

## Диагностика

Перед тем как искать ошибку в коде, запустите самопроверку:

```powershell
$env:PYTHONPATH = "D:\tg\src"
D:\tg\.venv\Scripts\python.exe -m iphone_monitor.doctor
```

Она проверяет настройки (интервал, режим Telegram), доступность фида Авито,
связь с Telegram, базу и то, не запущен ли второй экземпляр бота. Каждая
строка `СТОП` — конкретная причина.

## Telegram: почему MTProto

С российских домашних провайдеров `api.telegram.org` блокируется по SNI, а
прямой MTProto тоже не проходит. Рабочая схема: локальный прокси TgWsProxy
(`127.0.0.1:1443`) + `TELEGRAM_TRANSPORT=mtproto`. Пока TgWsProxy запущен,
бот может писать и читать сообщения. Если прокси выключен, уведомления
копятся в очереди и уходят после его включения.

На сервере (Амвера и т.п.) Bot API обычно доступен напрямую, поэтому там
достаточно `TELEGRAM_TRANSPORT=botapi` без прокси.

## Запуск

```powershell
D:\tg\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:PYTHONPATH = "D:\tg\src"
D:\tg\.venv\Scripts\python.exe -m iphone_monitor.main
```

Автозапуск и перезапуск после падения — `tasks/run-bot.ps1`. Скрипт держит
один экземпляр бота (файл-замок `data/bot.lock`), пишет вывод в
`data/launcher-*.log`, а события самого бота — в `data/bot.log`.

## Перенос на сервер (Амвера)

Бот в Docker-образе (`Dockerfile`), без привязки к Windows: в Amvera создайте
проект типа «Docker», загрузите проект, смонтируйте постоянное хранилище в
`/data` и задайте переменные окружения из `.env`. На сервере Telegram Bot API
доступен напрямую, поэтому `TELEGRAM_TRANSPORT=botapi` и `TELEGRAM_PROXY`
оставьте пустыми — прокси нужен только дома.

Один и тот же `.env` не подходит для двух машин одновременно: на сервере
должен работать только один экземпляр бота (файл-замок `/data/bot.lock`
защищает от двойного запуска в пределах одной машины).

### Как перенести историю на сервер

Новая машина начинает с пустой базы: она не помнит, какие объявления уже
видела, и не знает, о каких уже сообщила. Чтобы бот не забыл это при переезде,
в репозитории лежит `assets/seed_state.json` — снимок состояния:

```powershell
# сделать снимок на старой машине (база должна быть не занята ботом)
& .\.venv\Scripts\python.exe tasks\make_seed_state.py
```

Бот при старте один раз вливает этот снимок в базу (история просмотров, уже
отправленные сделки, цены для расчёта рынка) и ставит отметку
`seed_state_applied` в метаданных, поэтому повторно вливать не будет.
Читатели (`chat_id`) в файл не попадают — на сервере их задаёт
переменная `TELEGRAM_CHAT_ID`. Путь к файлу меняется через
`SEED_STATE_PATH`, пустое значение отключает перенос.

### Сколько это стоит и что делать, когда деньги кончатся

Приложение арендуется в Amvera: тариф «Пробный» — 170 ₽ за 30 дней, деньги
списываются с баланса аккаунта понемногу (примерно 4–7 ₽ в сутки). Пока на
балансе есть деньги, контейнер работает сам и перезапускается после сбоев.
Когда баланс кончится, Amvera заморозит приложение: бот перестанет опрашивать
Авито, уведомления и сайт остановятся — но ничего не потеряется, история
останется в /data.

Что делать, когда это случится (по решению владельца):

1. Пополнить баланс в личном кабинете Amvera — контейнер поднимется сам,
   история и настройки останутся на месте.
2. Или на время вернуть бота на домашний компьютер: запустить
   D:\tg\tasks\run-bot.ps1 (нужен включённый компьютер и TgWsProxy,
   потому что дома Bot API заблокирован). Перед этим убедитесь, что облако
   действительно остановлено — иначе объявления будут приходить дважды.
3. После переезда в обратную сторону снова соберите
   tasks\make_seed_state.py и закоммитьте assets/seed_state.json.

Проверить, жив ли облачный бот, можно по снимку сайта: поле status.host
начинается с run-pereekyp- (это Amvera), а status.heartbeat_iso должен
быть свежим (не старше 30 минут при опросе раз в 15 минут).

## Публикация данных на сайте

Бот пишет снимок состояния: статус (живой/нет, пауза, число сбоев
источника, время heartbeat) и последние уведомления. Есть три способа
доставить его на сайт.

1. `GITHUB_TOKEN` + `GITHUB_REPO` — рекомендуемый. Бот коммитит снимок в
   `site/site-data.json` (по умолчанию) через GitHub API, а workflow
   `Deploy website to InfinityFree` публикует его на хостинг. Пароль FTP
   боту не нужен вообще: он живёт в секретах GitHub Actions.
2. `SITE_FTP_HOST` / `SITE_FTP_USER` / `SITE_FTP_PASSWORD` — прямая
   загрузка по FTP (`SITE_FTP_DIR`, по умолчанию `/htdocs`).
3. Ничего не задано — снимок лежит в `data/site-data.json` и никуда не
   уходит.

`SITE_EXPORT_INTERVAL_SECONDS` (по умолчанию 1800) задаёт, как часто бот
обновляет снимок; сразу после нового уведомления снимок публикуется
принудительно, чтобы сайт не отставал от Telegram.

В снимке есть блок `status.diag` — он нужен, чтобы проверять бота на
сервере, не заходя в контейнер: `host` (имя машины, по нему видно, кто
опубликовал снимок — домашний ПК или Amvera), `last_cycle` (время цикла,
сколько объявлений получено, сколько новых, сколько уведомлений, лучшая
маржа), `last_source_error` (последняя ошибка источника и признак
`rate_limited`), а также `seen_total`, `pending_notifications` (очередь
недоставленного в Telegram) и `subscribers`.

Читать снимок с сервера: `gh api repos/<owner>/<repo>/contents/site/site-data.json`.
Если `pending_notifications` растёт, а `notified` стоит на нуле — на сервере
не проходит Telegram, тогда нужен `TELEGRAM_TRANSPORT=mtproto` и прокси.

## Логи и закрытый раздел `/admin/logs.html`

Каждое важное действие бота — одна JSON-строка в `LOG_PATH` (`data/bot.log`,
ротация 5 МБ × 3 файла). Запись выглядит так:

```json
{"timestamp": 1793451254.52, "timestamp_iso": "2026-10-31T12:54:14.520Z",
 "level": "INFO", "event": "listing_notified", "status": "success",
 "component": "telegram", "cycle_id": "20261031T125414Z-2ff247",
 "listing_id": "8499243676",
 "details": {"price_rub": 58990, "margin_rub": 18110}}
```

* `timestamp` — прежнее число (эпоха), чтобы не ломать старых читателей;
  `timestamp_iso` — то же время в UTC по ISO-8601.
* `status` — только `started`, `success`, `failed`, `skipped`, `queued`,
  `retried`; `component` — `bot`, `monitor`, `store`, `telegram`, `market`,
  `publish`, `logs_api`.
* `cycle_id` связывает все записи одного цикла опроса, `listing_id` — все
  записи одного объявления.
* Пароли, токены Telegram/GitHub, cookie, заголовки авторизации и учётные
  данные из URL маскируются (`[redacted]`) ещё до записи. От исключений
  остаётся только `Тип: сообщение` без traceback; переводы строк в
  пользовательских строках заменяются, поэтому подделать отдельную запись
  лога нельзя.

Основные события: `bot_started`/`bot_stopped`, `telegram_ready`,
`source_ready`, `cycle_started`/`cycle_finished`/`cycle_failed`,
`listing_stored`, `listing_skipped`, `listing_notified`,
`telegram_delivery_sent`/`telegram_delivery_queued`, `site_snapshot_written`,
`site_snapshot_committed`, `site_snapshot_uploaded`, `site_publication_state`.

### Где работает API логов

Статический сайт на InfinityFree не может читать файл лога: у него нет доступа
к контейнеру бота. Поэтому защищённый API (`src/iphone_monitor/logs_api.py`)
запускается рядом с ботом — в том же процессе Amvera (или отдельным процессом
на машине, где лежит `LOG_PATH`). `site/server.py` — только локальный
предпросмотр, production-защиты в нём нет.

Включение:

```env
ADMIN_LOGS_ENABLED=1
ADMIN_LOGS_PASSWORD=<длинный пароль>
ADMIN_LOGS_SESSION_SECRET=<случайные 32+ символа>
ADMIN_LOGS_PORT=8787           # в Amvera обычно PORT, выданный платформой
ADMIN_LOGS_CORS_ORIGIN=https://<ваш-сайт>   # точный origin, без "*"
```

Без `ADMIN_LOGS_PASSWORD` или при секрете короче 16 символов API отвечает
`503` и не отдаёт ничего. Пароль проверяется сравнением постоянного времени,
попытки входа ограничены (`ADMIN_LOGS_MAX_LOGIN_ATTEMPTS`,
`ADMIN_LOGS_LOCKOUT_SECONDS`), сессия живёт `ADMIN_LOGS_SESSION_TTL_SECONDS`
и подписана HMAC-SHA256. Токен страница держит только в памяти — ни
`localStorage`, ни `sessionStorage`, ни cookie (cookie-режим
`ADMIN_LOGS_COOKIE_MODE=1` — опция для одного origin на HTTPS).

### Как открыть

1. `https://<сайт>/admin/logs.html` — форма входа.
2. Если API на другом домене, добавьте `?api=https://<api-хост>`: адрес
   запоминается только в адресной строке, страница обращается к
   `/api/admin/logs/login` и `/api/admin/logs` этого хоста.
3. После входа — лента «время — действие — статус — детали», фильтры по
   статусу, событию, компоненту, диапазону времени и поиску, кнопка
   «Загрузить ещё».

Проверка без риска:

```bash
curl -i https://<api-хост>/api/admin/logs        # 401 и никаких данных
curl -i -X POST https://<api-хост>/api/admin/logs/login -d '{"password":"неверный"}'
                                                  # 401; после 5 попыток — 429
curl -i https://<api-хост>/api/admin/logs/health   # 200, без секретов
```

API всегда отдаёт `Cache-Control: no-store` и `X-Robots-Tag: noindex`,
читает только хвост `LOG_PATH` и соседние `*.1…N`, не принимает путь из
запроса, ограничивает ответ `ADMIN_LOGS_MAX_LIMIT` (200 по умолчанию) и не
отдаёт файл целиком.

### Статусы публикации сайта

Снимок, коммит и деплой — разные вещи, и лог их не смешивает:

* `site_snapshot_written` — файл записан локально (сайт ещё не обновлён);
* `site_snapshot_committed` — снимок ушёл в GitHub (`deploy_confirmed: false`,
  `stage: awaiting_deploy`); сама публикация ждёт workflow;
* `site_snapshot_uploaded` — файл выгружен по FTP прямо в каталог сайта
  (`deploy_confirmed: true`);
* `site_publication_state` — итог: `published`, `awaiting_deploy` или
  `local_only`.

Если нужен настоящий признак «сайт задеплоен», включите
`GITHUB_DEPLOY_CHECK=1` и дайте `GITHUB_TOKEN` право читать Actions: бот
спросит workflow `deploy-site.yml` по sha коммита и запишет
`site_deploy_confirmed` либо `site_deploy_pending` (статус `queued`/`retried`).
Без этой проверки запись остаётся «ожидает деплоя» — коммит никогда не
выдаётся за подтверждённую публикацию.

## Команды бота

`/start` — подписаться на уведомления, `/stop` — отписаться,
`/status` — состояние, `/pause` и `/resume` — пауза мониторинга,
`/plan` — тариф и остаток сигналов на сегодня, `/upgrade` — тарифы и цены,
`/track` — сводка по сделкам (прибыль, оборот, средняя маржа).

## Тарифы и лимиты

Каталог тарифов — единственный источник правды: `src/iphone_monitor/plans.py`.

| Тариф | Цена | Сигналы | Задержка | Фильтры | Трекер |
|---|---|---|---|---|---|
| Free | 0 ₽ | 3 в сутки | до 30 мин | 1 | нет |
| Pro | 690 ₽/мес · 6 900 ₽/год | без лимита | сразу | 20 | да |
| Instant | 1 490 ₽/мес · 14 900 ₽/год | без лимита | сразу, приоритет | 50 | да |
| Business | 3 900 ₽/мес · 39 000 ₽/год | без лимита | сразу, 5 мест | 50 | да |

Лимит проверяется на сервере, в `Monitor._send`, а не в кабинете. Free не теряет
сигнал: он кладётся в ту же очередь `pending_notifications` с `deliver_at` на
30 минут вперёд и уходит, когда срок наступил (это делает
`flush_pending_notifications`). Платные тарифы отправляют сразу.

Аккаунт чата создаётся при первом обращении. Тариф по умолчанию задаёт
`DEFAULT_PLAN` (по умолчанию `pro`, чтобы действующие подписчики не оказались
на Free после обновления); новый человек получает Free через `/start`.
Расход сигналов — в `usage_counters` (ключ — сутки UTC), сделки — в `deals`,
сводка считается в `SeenStore.deals_summary`.

Что сделано в этом срезе: `plans.py`, таблицы `accounts`/`usage_counters`/`deals`,
очередь с задержкой, команды `/plan`, `/upgrade`, `/track`, логи
`notification_delayed` / `notification_suppressed` / `listing_skipped`
(reason `limit_reached`). Платежи, экраны кабинета и фильтры на человека —
следующий срез; разбор рынка — `docs/competitive-analysis.md`.
